## 0. The three questions the brief asks

**What can currently go wrong for a Gloo user, per role?**
The role/permission model is coherent and tenant *reads* are solidly scoped. The danger is
concentrated in **identity/auth** and in **write-side authorization**: an unauthenticated
person can claim any not-yet-activated account in any tenant; several mutation endpoints
trust foreign-key ids and status transitions from the request body without an
ownership/organization check. Full register in §3.

**Why ~15 seconds per navigation, and where is the time?**
Not query volume. Warm production server latency for a real authenticated request is
**~0.37 s** (measured tonight, §4.1). A *flat* 15 s regardless of page matches exactly one
constant in the code: `connectionTimeoutMillis: 15_000` in `lib/prisma.ts`, hit when a
pooled connection cannot be acquired (stale post-freeze socket, or the 2-connection pool
saturated). Next's router then turns the failed RSC fetch into a full document reload, which
presents as "slow but eventually loads". Root cause + measurement plan in §4.

**Can fixes start tomorrow without re-discovery?** Yes — §7 is an ordered, file-level backlog.

## 4. Performance — root cause & register

### 4.1 Measured tonight (production, unauthenticated, 6 warm samples)

| Probe | TTFB (warm) | Isolates |
|---|---|---|
| Edge static asset | ~0.22 s | India → Mumbai edge (floor) |
| `/api/users/me`, no cookie (0 queries) | ~0.25 s | reaching the function |
| `/api/users/me`, bogus cookie (1 query) | ~0.37 s | + one DB round trip |
| `/login` HTML | ~0.21 s | — |

`X-Vercel-Id: bom1::…` — the region fix from 2026-09-14 is still in place. **A warm authenticated
request costs ~0.37 s.** The code's query counts add ~1–4 s on the heaviest pages. **Neither
explains a flat 15 s.**

### 4.2 Root cause of the 15 s (CONFIRMED-CODE, corroborated by two agents)

The only 15-second constant on the path is **`connectionTimeoutMillis: 15_000` in
`lib/prisma.ts:78`**. `pg-pool` applies that timeout to *queued waits for a pooled
connection*, not just TCP connects. With **`max: 2`** connections (unless prod
`DATABASE_URL` is on port 6543 — unverified) and no statement/query timeout anywhere, either
a **stale socket after a Vercel instance thaw** (idle timers don't run while frozen) or a
**saturated 2-connection pool** stalls a request for exactly 15 s. Next's router converts the
failed/timed-out RSC fetch into a **full document reload**, so the user experiences "slow but
it loads." **Tell-tale in the browser:** a second Document request + console
`Failed to fetch RSC payload … Falling back to browser navigation`.

## 6. Cross-role workflow (CONFIRMED-LIVE)

HoD creates+assigns a task to a designer → **task created**, **designer notified**
(`TASK_ASSIGNED`, correct `/tasks?task=` link), **designer's own list shows it**, **DB has one
`TASK_ASSIGNED` row scoped to Gloo, zero in Other Co**. The core assign→notify→recipient loop
is intact for this path. Gaps found are in *other* transitions (accept/decline surfacing
QA-008, reassignment/deletion notify-nobody QA-018, frozen drawer QA-019), not in the basic
assignment loop.
